# My Knowledge OS v0.3 — Knowledge UX Design Spec

Date: 2026-07-22
Status: approved design, pending user review of the written specification
Target: `mko 0.3.0`, KB `schema_version: 2`
Decision: clean break from the v0.2 KB data contract; retain and adapt proven Core safety code

## 1. Purpose

v0.2 proved the deterministic Asset, Source, Knowledge, revision, and human-approval primitives,
but normal use still exposes too much of the internal pipeline. Setup assumes that a KB already
exists, ordinary registration requires the user to understand several commands, and review offers
approval or defer without a natural feedback-and-regeneration loop.

v0.3 makes the system usable through three primary surfaces:

1. **Codex conversation** for setup, registration, summarization, knowledge creation, review, and
   natural-language feedback;
2. **Obsidian** for reading, browsing, filtering, and seeing review queues;
3. **`mko` Core/CLI** as the deterministic authority for files, IDs, revisions, state transitions,
   validation, and approval records.

The user should not need to know an Asset ID, repository path, temporary bundle path, or internal
command during ordinary use.

## 2. Product priorities

The previously approved priorities remain unchanged:

1. personal growth;
2. work productivity;
3. a durable personal agent substrate;
4. portfolio/showcase extraction.

The main knowledge artifact is not merely a summary. It captures grounded facts, concepts,
trade-offs, interpretations, uncertainties, and eventually the user's own judgment while keeping
those epistemic categories separate.

## 3. Scope

### 3.1 Included in v0.3

- one guided setup flow for macOS and Windows;
- new Personal KB scaffolding with KB schema version 2;
- easy PDF Asset registration;
- Source summarization followed by an explicit knowledge-registration question;
- an explicit "register as knowledge" fast path;
- Inbox batch summarization and numbered knowledge candidates;
- a unified Source/Knowledge review queue;
- full, readable review cards instead of title-only concept lists;
- explicit `approve`, `request changes`, and `defer` decisions;
- durable natural-language feedback linked to the exact reviewed revision;
- regeneration with an exact diff from the previously displayed/approved revision;
- grounded LLM analysis separated from Source facts;
- Obsidian Home, Review Queue, and Knowledge Library views;
- a provider- and media-independent content-bundle interface;
- a Google Drive filesystem provider and PDF extractor as the first implementations;
- actionable diagnostics, partial-success reporting, and resumable retries;
- explicit, user-approved Git synchronization between devices without automatic conflict
  resolution;
- a new machine contract for the v0.3 Skill;
- macOS and Windows verification plus a user-assisted Google Drive smoke test.

### 3.2 Explicitly deferred

- PPTX, DOCX, spreadsheet, image, audio, and video extractors;
- direct Google Drive API integration;
- Obsidian plugin or separate desktop/web GUI;
- direct editing of managed Source/Knowledge records in Obsidian as a supported feedback path;
- unattended Git commit, push, pull, or pull-request creation;
- background Inbox watchers or daemons;
- vector search, RAG, and embedding infrastructure;
- autonomous promotion or autonomous approval;
- Shared and Work cross-scope promotion workflows.

## 4. Clean-break policy

There are no valuable v0.2 user records and no external users. Preserving the frozen v0.2 record
shape would force the new unified review lifecycle, generic content bundle, and feedback records to
carry unnecessary compatibility branches. v0.3 therefore introduces a new KB contract.

The clean break applies to **stored data and machine contracts**, not to proven implementation
techniques:

- reuse and adapt bounded scans, no-follow file handling, path policy, hashing, atomic publication,
  compare-at-commit validation, and deterministic rendering;
- do not mutate, delete, or silently migrate a v0.2 KB;
- detect a v0.2 KB before any write and return `kb_schema_unsupported` with a safe instruction to
  archive it and create a v0.3 KB;
- retain the old repository history and release/tag for forensic reference;
- do not implement a v0.2-to-v0.3 data migration in this release;
- use KB `schema_version: 2` and machine output `json-v2` so old and new contracts cannot be
  mistaken for one another.

## 5. Architecture and ownership

```text
User
  | natural-language request, feedback, explicit approval
  v
Codex Skill
  | allowlisted json-v2 commands and bounded semantic responses
  v
mko CLI / Core
  | validated canonical Markdown and review records
  v
Personal KB
  +-- Asset registry
  +-- Sources
  +-- Knowledge
  +-- Reviews
  +-- Obsidian views
```

### 5.1 Codex owns

- interpreting a small set of user intents;
- presenting concise setup, summary, queue, review-card, and diff views;
- producing bounded Source and Knowledge semantic responses from an untrusted content bundle;
- asking whether a completed Source summary should be registered as Knowledge;
- relaying explicit feedback or approval to the Core;
- explaining exact recovery steps returned by the Core.

Codex does not write managed Markdown/YAML directly, calculate canonical IDs or revisions, infer
approval from ambiguous language, or execute Git publication actions.

### 5.2 Core owns

- all durable records and derived IDs;
- provider import/capture, fingerprints, and content identity;
- extraction-bundle validation and provenance;
- record rendering, replacement, state transitions, and review events;
- exact revision binding and compare-at-commit publication;
- one repository mutation lock shared by every cooperating v0.3 writer;
- validation, queue computation, search visibility, and diagnostics;
- stable machine-readable `json-v2` output.

### 5.3 Obsidian owns

- human reading and navigation;
- property-based Bases, filters, links, and local graphs;
- user-authored Canvas and non-managed notes.

Obsidian is not a second state machine. Managed records remain Core-owned, and user feedback is
submitted through Codex/CLI in v0.3.

### 5.4 Git owns

- change history, comparison, transport between devices, and recovery after human review.

Approval and Git publication are separate. Approval never stages, commits, or pushes. A distinct
guided sync flow may inspect Git state and, after exact user approval, perform a bounded commit,
fast-forward pull, or push. It never resolves a divergence or conflict automatically.

## 6. Terminology and pipeline

The UI and documentation use three distinct verbs:

| Stage | User-facing term | Meaning |
|---|---|---|
| Asset | **register** | preserve/import the file and write deterministic file metadata |
| Source | **summarize** | extract content and write a grounded document summary |
| Knowledge | **register as knowledge** | synthesize concepts, analysis, uncertainty, and links |

Canonical flow:

```text
Asset register
  -> Source summarize
       -> ask "Register this as a knowledge note?"
            -> no/later: keep the Source only
            -> yes: write Knowledge and enter unified review
```

An explicit user request such as "이 PDF 지식으로 등록해줘" skips only the question. It does not
skip registration, extraction, validation, review, or explicit approval.

## 7. Guided setup

### 7.1 Entry point

After installing the Skill once from the canonical GitHub repository, the user says:

> My Knowledge OS 시작해줘

The Skill invokes a setup-oriented machine flow. `mko setup` remains available as the terminal
equivalent.

The installed Skill bundles two deterministic bootstrap scripts, one for macOS and one for
Windows, plus a versioned manifest containing the exact allowed release URL, platform, size, and
SHA-256 digest. They download only that Skill-pinned `mko` binary, verify it against the local
manifest before installation, and install to the documented per-user destination. They do not
trust a remotely downloaded checksum file or execute a downloaded shell/PowerShell script. Private
GitHub access uses an existing host/GitHub CLI login without copying its token into arguments or
the KB. Network access and destination writes require host approval; without it, the Skill prints
the exact manual command. This bootstrap closes the clean-machine gap before `mko setup plan`
exists.

### 7.2 Setup sequence

1. inspect platform and installed `mko` version;
2. if the CLI is missing or stale, present the exact version/source/checksum and request permission
   through a supported host approval surface before installation or upgrade;
3. discover an existing v0.3 Personal KB in known locations;
4. offer to clone an existing private GitHub KB or scaffold a new local Personal KB;
5. request confirmation through that same explicit approval boundary before any repository
   creation, clone, or remote change;
6. detect Google Drive filesystem account roots;
7. select or create the exact Personal Inbox beneath the chosen account;
8. write machine-local paths and provider configuration outside Git;
9. install/repair the managed validation hook;
10. scaffold the Obsidian view definitions without overwriting user-owned notes;
11. run complete diagnostics;
12. print one successful next action: select a PDF and say "이 PDF 요약해줘".

Codex uses a structured two-phase setup contract rather than driving the interactive command:

```text
mko setup plan --format json-v2
  -> immutable plan id, exact steps, destinations, effects, risks, and required approvals

mko setup apply --plan <id> --format json-v2
  -> apply only the still-current approved plan
```

The plan expires, is single-use, and is invalidated by any relevant filesystem, repository,
provider, version, or destination change. If the Codex host cannot provide a per-action human
approval surface, the Skill stops and asks the user to run the interactive `mko setup` flow in a
real terminal. The Core does not treat a plain agent-generated flag as proof of human consent.

### 7.3 Distribution

Easy setup cannot depend on a pre-existing Rust toolchain. v0.3 distribution includes versioned,
checksum-published CLI binaries for the supported macOS and Windows targets. The Skill installer
and CLI installer remain separate security boundaries:

- Skill installation is a one-time user-approved GitHub action;
- CLI installation/upgrade is another explicit action showing source, version, destination, and
  checksum;
- a source build with Cargo remains a developer fallback, not the normal user path;
- authentication tokens and machine paths are never written to the KB.

### 7.4 Idempotency and failure behavior

- setup is preflighted before any write;
- rerunning setup reuses valid existing state and repairs only owned/generated files;
- existing user files are never overwritten silently;
- a partial failure reports applied steps, unapplied steps, and the one next recovery action;
- rollback failure is reported honestly; setup never claims a complete rollback without evidence;
- old-schema discovery blocks all mutation until the user chooses a new v0.3 destination.

The first Inbox registration is non-destructive: registering an existing Inbox file does not move,
rename, delete, or clean it and therefore does not require a backup attestation. Backup evidence is
required only for a future destructive cleanup/archive action, which is outside v0.3. Imports from
outside the Inbox copy the file and preserve the original.

Successful output is concise:

```text
My Knowledge OS 준비 완료

✓ Personal KB 연결
✓ Google Drive Inbox 연결
✓ Codex Skill/CLI 버전 일치
✓ Obsidian 보기 파일 생성
✓ 저장소 검사 통과

PDF를 선택하고 “이 PDF 요약해줘”라고 말하세요.
```

If setup also verifies a supported Obsidian installation, Vault registration, and Bases support,
the fourth line may instead say `✓ Obsidian Dashboard 연결`. It must not claim that merely because
view files were generated.

### 7.5 Two-device Git synchronization

Google Drive stores Assets; it does not synchronize KB Git history. Setup says this explicitly.
On a second device, setup validates Git authentication, clones the same private repository, checks
the provider marker, and refuses writes when the clone is stale, dirty in managed paths, diverged,
or conflicted.

`mko sync status` is read-only. A guided `동기화해줘` flow presents exact commits/files and then
requests separate host/TTY approval for commit, fast-forward pull, and push. Only fast-forward pull
is automatic after approval; divergence/conflict stops with manual recovery guidance. The system
never stores Git credentials, invents commit scope, includes unreviewed unrelated files, or claims
Drive synchronized the KB.

## 8. Provider and media extension model

The Skill never says "read from Google Drive" or "parse a PDF" as its general contract. It asks
the Core to resolve an Asset and consumes a normalized prepared-content bundle.

### 8.1 Provider adapter

Conceptual provider operations:

```text
discover()
inspect(locator)
open_readonly(locator)
import(source)
fingerprint(locator)
```

v0.3 implements `google-drive-filesystem` using the locally mounted streaming filesystem. Future
providers may implement local filesystem, OneDrive, NAS, S3, or another cloud service without
changing Source/Knowledge semantic contracts.

The provider root contains a small synced marker with a random `provider_instance_id`. The KB
stores that non-secret ID, while each machine-local profile maps it to a local mount path. Setup on
a second device must read the same marker and reconcile a sample of registered logical
locator/fingerprint pairs before enabling writes. A matching folder name alone is not sufficient
to bind an account.

### 8.2 Extractor adapter

Conceptual extractor operations:

```text
supports(media_type)
extract(asset_snapshot)
validate(output)
```

Future adapters may cover:

- PDF: text, pages, tables, image references;
- PPTX: slide text, speaker notes, and slide locators;
- spreadsheets: sheets, ranges, tables, formulas, and cell locators;
- images: OCR, regions, diagram descriptions;
- video/audio: transcripts, timestamps, and selected keyframes;
- web/documents: sections, URLs, headings, and source locators.

### 8.3 Prepared content bundle

The normalized machine artifact is `prepared-content-v2`:

```yaml
schema_version: 2
artifact_type: prepared_content
bundle_id: prepared-content-sha256-<hash>
content_digest: sha256:<hash>
asset_id: personal-asset-<hash>
asset_fingerprint: sha256:<hash>
media_type: application/pdf
trust: untrusted_document_content
extractor:
  name: pdf-text
  version: <version>
metadata:
  title: <string | null>
  authors: [<string>, ...]
  created_at: <RFC3339 | null>
content_blocks:
  - id: block-0001
    block_type: text
    locator: page:1
    text: <bounded string>
  - id: block-0002
    block_type: table
    locator: sheet:Summary!A1:D10
    columns: [<string>, ...]
    rows: [[<scalar>, ...], ...]
  - id: block-0003
    block_type: image
    locator: slide:3/image:1
    alt_text: <bounded string | null>
    artifact_id: artifact-0001
  - id: block-0004
    block_type: transcript
    locator: time:00:01:20-00:01:45
    speaker: <string | null>
    text: <bounded string>
artifacts:
  - id: artifact-0001
    media_type: image/png
    content_digest: sha256:<hash>
    size_bytes: <integer>
    provider_locator: <derived-artifact logical locator>
```

Rules:

- every content and metadata field is untrusted document data;
- embedded instructions, URLs, approval requests, and secrets are never executed;
- the Core binds the bundle to the exact Asset fingerprint;
- `content_digest` is calculated from one specified canonical serialization of all semantic bundle
  fields, and `bundle_id` is derived from that digest;
- blocks, total bytes, extraction time, and nesting are bounded;
- every statement written as grounded fact must reference one or more locators where the format
  supports them;
- format-specific details remain in block metadata, not in the Knowledge contract;
- `block_type` is a deny-unknown-fields discriminated union; v0.3 PDF emits `text` and may emit
  `table`, while deterministic fake extractors freeze validation for every declared variant;
- every non-inline artifact is listed in `artifacts`, digest-bound, size-bounded, and referenced by
  ID; dangling/duplicate artifact IDs fail validation;
- large multimedia uses the artifact manifest rather than raw bytes.

Prepared bundles are reproducible artifacts rather than KB records. After extraction, the Core
publishes the content-addressed bundle into the same-scope provider's hidden derived-artifact area;
Google Drive therefore makes the exact bundle available on the second device without putting bulk
text in Git. A local machine-private cache may retain a copy for performance. Both locations are
excluded from Inbox discovery. Every Source and Knowledge revision stores `bundle_id`,
`content_digest`, Asset fingerprint, and extractor version.

If both copies are missing, the Core re-extracts from the same provider Asset with the pinned
extractor version. Release artifacts retain every extractor version referenced by an accepted v0.3
bundle. Regeneration continues only when the canonical digest matches. If the required extractor
cannot be obtained or the digest differs, the Core blocks with `evidence_basis_unavailable` or
opens a new evidence basis requiring fresh Source/Knowledge review; it never substitutes silently.

## 9. v0.3 KB model

### 9.1 Layout

```text
personal-kb/
├── knowledge-os.yaml
├── assets/
│   └── registry/
├── sources/
│   └── <source-id>/
│       ├── current.yaml
│       └── revisions/
│           └── <revision>.md
├── knowledge/
│   └── <knowledge-id>/
│       ├── current.yaml
│       ├── revisions/
│       │   └── <revision>.md
│       └── judgments/
│           └── <judgment-revision>.md
├── reviews/
│   └── <review-id>.md
├── views/
│   ├── HOME.md
│   ├── review-queue.base
│   ├── knowledge-library.base
│   └── records/
└── .mko/
    └── generated-manifest.yaml
```

`views/` is Core-owned but regenerable. The manifest identifies exactly which paths the Core may
repair. User-authored Canvas files and notes outside those owned paths are never overwritten.

Source and Knowledge revision documents are immutable and content-addressed. `current.yaml` is a
small CAS-updated pointer to the active revision and its evidence basis. Approval does not mutate a
Source or Knowledge revision. Review events are the authoritative approval state, and `views/`
contains regenerable Obsidian projections that combine the current pointer with review events.
This preserves an exact previous approved body for diffing even when Git publication has not yet
occurred.

The repository contract marker is explicit and checked before every mutating command:

```yaml
system: my-knowledge-os
contract_version: 0.3.0
schema_version: 2
scope: personal
```

### 9.2 Asset

An Asset contains deterministic file identity and provider facts only:

- ID and scope;
- title fallback derived from the filename;
- media type and Asset class;
- provider type and logical locator;
- size, modified time, and cryptographic fingerprint;
- processing state, last successful step, and actionable last error;
- creation/update audit fields.

Semantic document metadata such as authors or abstract belongs to extraction/Source, not capture,
unless the provider itself supplies a trustworthy field with explicit provenance.

### 9.3 Source

A Source is the document-facing reading record. It includes:

- normalized title, authors, and publication metadata extracted from the content;
- one-sentence and general summaries;
- key claims with evidence locators;
- limitations stated by the document;
- relevance tags and a knowledge-value recommendation;
- generation provenance and exact Asset/bundle fingerprint;
- an immutable content revision. Review status and approved revision are derived from Review
  events rather than written into the immutable body.

The bounded `source-response-v2` shape is frozen before implementation:

```yaml
title: <non-empty string>
authors: [<string>, ...]
publication_date: <date | null>
one_sentence_summary: <bounded string>
general_summary: <bounded string>
key_claims:
  - text: <bounded string>
    evidence_locators: [<locator>, ...]
limitations:
  - text: <bounded string>
    basis: stated | observed_missing_evidence
    evidence_locators: [<locator>, ...]
tags: [<normalized tag>, ...]
knowledge_recommendation:
  outcome: recommend | reference_only | archive
  reasons: [<bounded string>, ...]
```

Every key claim requires evidence. A `stated` limitation requires evidence; an
`observed_missing_evidence` limitation names a mechanically explicit basis and may have no locator.
The Core validates enums, bounds, locator existence, and conditional cardinality rather than trying
to understand whether free prose “sounds grounded.”

### 9.4 Knowledge

A Knowledge note contains four epistemically separated sections:

1. **Source-grounded knowledge**: concepts, definitions, results, formulas, and claims, each with
   evidence locators;
2. **LLM analysis**: practical meaning, connections, trade-offs, and possible failure modes;
3. **Counterarguments and uncertainty**: alternative interpretations, weak evidence, missing data,
   and verification questions;
4. **User judgment**: a human-owned section, empty by default and never invented by the LLM.

LLM analysis is valuable but must never be rendered as a Source fact. Every generated analytical
unit has an epistemic label (`interpretation` or `hypothesis`), a confidence band, supporting
locators where applicable, and counter-evidence/unknowns.

For high-risk domains such as finance, the semantic contract requires explicit counterarguments
and verification questions. A Knowledge note is not financial, medical, or legal advice.

The bounded `knowledge-response-v2` uses deterministic enums rather than prose conventions:

```yaml
synthesis: <non-empty bounded string>
units:
  - kind: fact | definition | formula | result | interpretation | hypothesis |
          counterargument | uncertainty | open_question
    title: <single-line string>
    body: <bounded string>
    confidence: high | medium | low
    basis: evidence | missing_evidence | conflicting_evidence
    evidence_locators: [<content block locator>, ...]
    tags: [<normalized tag>, ...]
```

Core rules are mechanical:

- `fact`, `definition`, `formula`, and `result` require `basis: evidence` and at least one valid
  evidence locator;
- `interpretation` and `hypothesis` cannot be rendered in the Source-grounded section;
- an empty evidence list is allowed only with `basis: missing_evidence` or
  `basis: conflicting_evidence` for `counterargument`, `uncertainty`, or `open_question`;
- the request carries a Core-owned `domain_policy` selected from KB configuration, not inferred by
  the LLM;
- a configured high-risk policy requires at least one `counterargument` and one `open_question`;
- no semantic response field exists for `user_judgment`.

User judgment is an independent annotation. The user invokes it explicitly (for example, "내
판단으로 추가: ..."), and the Skill relays the exact quoted text without rewriting through a
review-session-bound `mko judgment set` operation. It creates an immutable human annotation
revision linked to the Knowledge revision; it is never generated or paraphrased by the LLM. If no
trusted host approval surface or TTY is available, this operation stops rather than attributing
agent text to the user.

### 9.5 Review record

Feedback and decisions are immutable, durable first-class records:

```yaml
id: personal-review-<id>
record_type: review
schema_version: 2
targets:
  - record_type: source
    record_id: <id>
    displayed_revision: sha256:<hash>
    decision: approve | request_changes | defer
    feedback: <string | null>
    supersedes_review_id: <id | null>
  - record_type: knowledge
    record_id: <id>
    displayed_revision: sha256:<hash>
    decision: approve | request_changes | defer
    feedback: <string | null>
    supersedes_review_id: <id | null>
created_at: <RFC3339>
```

All fields in a Review record are immutable. A later `review_resolution` event references the
original review ID, target record ID, and resulting revision; no event is edited in place. For
approval, one atomic Review event containing every selected target revision is authoritative.
Because approval state is derived from that single event rather than copied into several target
files, approving a combined Source/Knowledge card is logically all-or-nothing with one atomic file
publication. Mixed decisions in one displayed card are also represented per target in that one
event. Per target/revision, a decision references the previous review head it supersedes. Core
publishes under the repository mutation lock and rejects a stale head. Multiple unsuperseded heads
are a detected blocked conflict, never resolved by timestamp ordering.

A feedback resolution is a separate immutable record:

```yaml
id: personal-review-resolution-<derived-hash>
record_type: review_resolution
schema_version: 2
review_id: <request_changes review id>
target_record_id: <id>
requested_revision: sha256:<hash>
resulting_revision: sha256:<hash>
bundle_id: prepared-content-sha256-<hash>
created_at: <RFC3339>
```

The ID is deterministically derived from `review_id`, target ID, and resulting revision. Retrying
an identical resolution is idempotent; a different body at that ID is a conflict. A resolution is
accepted only while the referenced `request_changes` outcome remains the unsuperseded review head
for `requested_revision`, the resulting immutable revision exists, and the current pointer names
that resulting revision. Otherwise it is stale and cannot change derived state.

## 10. User journeys

### 10.1 Summarize one selected PDF

User:

> 이 PDF 요약해줘

Flow:

1. resolve current Personal context and run health preflight;
2. register/import the Asset if necessary;
3. extract `prepared-content-v2` from the exact registered fingerprint;
4. produce and validate a bounded Source response;
5. publish an unreviewed Source revision through the Core;
6. display title, one-line summary, key points, limitations, and warnings;
7. ask exactly once: "이 내용을 지식노트로 등록할까요?";
8. if no/later, stop with the Source available for review;
9. if yes, continue to Knowledge creation and unified review.

### 10.2 Register one selected PDF as knowledge

User:

> 이 PDF 지식으로 등록해줘

The same pipeline runs, but step 7 is skipped because the user already gave explicit knowledge
intent. Source and Knowledge remain distinct records and revisions even when displayed in one
review card.

### 10.3 Process the Inbox

User:

> Inbox 정리해줘

The Core performs a bounded scan, reuses existing Assets by fingerprint, and returns per-item next
actions. The Skill summarizes eligible PDFs to Source, preserves per-item successes, and then shows
a numbered list:

```text
1. IMM Tracking Survey — 지식화 추천
2. Sensor Manual — 참고자료 유지 추천
3. Existing Paper — 기존 자료와 동일
4. Offline Paper — 다운로드 필요
```

The user can choose numbers or titles. Number mapping is presentation-session-local; all durable
operations use stable Core IDs and revisions returned by the Core. Batch mode never auto-promotes
every recommendation.

### 10.4 Duplicate and changed inputs

- same fingerprint: reuse the existing Asset and show its current Source/Knowledge/review state;
- same filename, different fingerprint: preserve a separate Asset with a stable disambiguated
  provider filename;
- registered provider content changed: block semantic processing and require an explicit new
  Asset registration or repair choice;
- Inbox-resident input: register non-destructively without backup attestation; a future destructive
  cleanup/archive operation must define and verify backup separately;
- no content is deleted to resolve a duplicate.

## 11. Unified review and feedback

### 11.1 Queue

`mko queue` computes one view from canonical Source and Knowledge states. It does not persist a
second queue state.

Every item includes:

- stable record IDs for the machine response;
- human title and session-local number;
- Source/Knowledge/both type;
- new/revised/blocked state;
- current and previous approved revisions;
- concept count, modified time, domain, and one next action;
- diagnostic details when blocked.

The default general knowledge search excludes unreviewed records. The review queue is the primary
place for pending content. An explicit advanced flag may include unreviewed results.

### 11.2 Review card

"2번 보여줘" produces:

1. Source-grounded summary;
2. key concepts and locators;
3. LLM analysis and trade-offs;
4. counterarguments, uncertainty, and open questions;
5. user judgment, if present;
6. diff from the last approved/displayed revision;
7. provider/Source links, provenance, and current review state.

Unlike v0.2 `show`, the card includes synthesis, concept bodies, tags, and locators rather than
only names and kinds.

### 11.3 Review session and explicit decisions

When a review card is requested, the Core creates a bounded, opaque review session tied to the
exact target IDs, bytes, and revisions that were returned for display. It returns one canonical
human-view card plus its digest; the Skill presents that card without summarizing, omitting, or
semantically rewriting it. Framing text may be added outside the card. The Skill may relay a
decision only after that exact display.

Open review sessions are machine-local, excluded from Git, expire after a bounded interval, and
carry no authority by themselves. Only a completed Core-published Review record is durable. A
session opened on one device cannot be used to approve from another device; the second device must
render a fresh card. Session capabilities are high-entropy, single-use, scoped to one decision,
stored with owner-only permissions, and consumed on successful publication. Replay returns
`review_session_consumed`; expiry returns `review_session_expired`.

Allowed decisions:

- `approve`: approve all displayed targets unless the user explicitly selects one;
- natural-language feedback: record `request_changes` and regenerate selected targets;
- `defer`: keep the records pending without changing their content.

Ambiguous input is not silently treated as defer or approval. Codex asks a short clarifying
question.

A chat message alone is not Core-verifiable evidence that a human approved an action. Therefore,
after the user says `승인`, the Skill requests the Codex host's explicit per-command approval for
the exact review-session apply operation. If the host cannot provide that independent approval
surface, the Skill may display and collect feedback but must direct final approval to the real-TTY
`mko review` flow. The security claim is consequently explicit: human approval is enforced by the
Core plus a trusted host approval surface, or by Core plus TTY—not by prompt text or Skill policy
alone.

Before any decision publication, the Core reacquires its managed lock, rereads the current target,
recomputes the revision from the actual bytes, and verifies the review session snapshot. Any
change, stale session, replacement, or mismatch returns `review_snapshot_stale` and requires a new
display. The single authoritative approval Review event is published with compare-at-commit
semantics. No separate target approval fields need a multi-file transaction.

The managed lock in that paragraph is one repository-wide mutation lock used by all v0.3 Asset,
current-pointer, Review, resolution, judgment, and generated-view writers. Personal KB throughput
does not justify a fragile multi-record lock protocol. Review apply holds that lock while it
rereads every target pointer and immutable revision, validates expected bytes/digests and review
heads, and publishes the one Review event. A writer cannot change any target pointer between the
final validation and event publication. Lock recovery follows the existing bounded, owner-checked,
non-destructive recovery policy.

### 11.4 Feedback and regeneration

Example feedback:

> 전이확률 설명을 더 구체적으로 쓰고, 실제 차량 추적에서의 실패 사례를 추가해줘.

Flow:

1. publish a `request_changes` review tied to the displayed revision;
2. prepare a regeneration request containing the original grounded bundle, current record, and
   human feedback as distinct inputs;
3. produce a new bounded semantic response;
4. publish a new unreviewed content revision through compare-at-commit;
5. preserve the previous approved revision and immutable feedback;
6. show an exact semantic/text diff and open a fresh review session;
7. publish an immutable `review_resolution` event only when the new revision is durably linked.

The LLM may apply the feedback but may not invent user judgment. If feedback requests unsupported
facts, the new note records that they are not established by the Source rather than fabricating
them.

### 11.5 Canonical state derivation

The queue derives state from current pointers, immutable revisions, and immutable Review events:

| Evidence | Derived state | Next action |
|---|---|---|
| no current revision | absent | create |
| current revision, no Review decision | unreviewed | display/review |
| current revision referenced by `defer` | deferred | display/review later |
| current revision referenced by `request_changes`, no resolution | changes_requested | regenerate/retry |
| feedback resolved to a new current revision | revised_unreviewed | display/diff/review |
| current revision referenced by authoritative `approve` | approved | none |
| approved older revision, newer current revision | revised_unreviewed | display/diff/review |
| missing/corrupt revision, stale pointer, evidence mismatch, or unresolved publication | blocked | diagnose/repair |

Selective review creates a Review event only for the selected target. A combined display can yield
one multi-target approval event, or separate feedback/defer events. If regeneration fails after a
`request_changes` event, the state remains `changes_requested`, the previous revision remains
readable, and retry resumes from the persisted feedback without claiming resolution.

## 13. CLI and Skill contract

### 13.1 Human CLI facade

```text
mko setup             guided setup and repair

mko status            overall Asset/Source/Knowledge/review counts and next action
mko queue             unified Source/Knowledge review queue

mko judgment          add/show exact human-owned Knowledge annotations
mko dashboard         Obsidian view check/repair
mko doctor            itemized diagnostics and exact recovery action
mko sync              inspect and explicitly synchronize KB Git state
```

Advanced extraction/write/repair commands remain available for tests and agent orchestration but
are documented separately from normal use.

### 13.2 Machine contract

- all Skill commands use `--format json-v2`;
- stdout contains exactly one typed JSON success or error envelope;
- human prompts/progress go to stderr only when allowed, and non-interactive commands do not prompt;
- stable command, result, state, and error enums replace parsing prose;
- machine output never requires the Skill to interpolate a document-provided locator into a shell
  command;
- paths returned for presentation are data, not executable command fragments;
- the Skill uses Core-returned next actions and allowlisted command templates only.

Every `json-v2` envelope has one of these top-level shapes and denies unknown fields:

```json
{"schema_version":2,"command":"queue","result":"ok","data":{}}
```

```json
{"schema_version":2,"command":"queue","result":"error","error":{"code":"...","message":"...","retryable":false,"next_action":"...","details":{}}}
```

Command-specific `data` schemas are versioned fixtures. Collection responses always include
`items`, `scan_complete`, `remaining`, and an opaque nullable `next_cursor`; bounded truncation is
not represented as success with a silently incomplete list. Setup/review plans include
`plan_or_session_id`, `expires_at`, `single_use`, exact target/effect digests, and
`approval_mode: host | tty`. The implementation plan must freeze schemas and cross-platform
goldens before command implementation.

The minimum DTOs are part of this design, not left to prose parsing:

```yaml
SetupPlanData:
  plan_id: <opaque id>
  expires_at: <RFC3339>
  precondition_digest: sha256:<hash>
  steps:
    - step_id: <enum>
      effect: read | create | modify | network | external
      destination: <sanitized logical destination>
      requires_human_approval: <bool>
  next_action: approve_plan | repair | none

QueueData:
  items:
    - item_id: <stable Core id>
      target_ids: [<record id>, ...]
      title: <string>
      item_type: source | knowledge | combined
      state: unreviewed | deferred | changes_requested | revised_unreviewed | blocked
      revisions: [sha256:<hash>, ...]
      next_action: display | regenerate | diagnose
  scan_complete: <bool>
  remaining: <integer>
  next_cursor: <opaque string | null>

ReviewOpenData:
  session_id: <opaque high-entropy id>
  expires_at: <RFC3339>
  single_use: true
  card_markdown: <canonical bounded string>
  card_digest: sha256:<hash>
  targets:
    - record_id: <id>
      displayed_revision: sha256:<hash>
      review_head_id: <id | null>
  approval_mode: host | tty

ReviewDecisionInput:
  session_id: <id>
  card_digest: sha256:<hash>
  target_decisions:
    - record_id: <id>
      decision: approve | request_changes | defer
      feedback: <bounded string | null>

ReviewApplyPlanData:
  plan_id: <opaque id>
  session_id: <id>
  decision_digest: sha256:<hash>
  effects:
    - record_id: <id>
      displayed_revision: sha256:<hash>
      decision: approve | request_changes | defer
  expires_at: <RFC3339>
  approval_mode: host | tty
```

The non-interactive approval path is two-phase: `mko review plan` validates the bounded decision
input and returns `ReviewApplyPlanData`; only the exact `mko review apply --plan <id>` command is
submitted to the host approval surface. Apply revalidates session, decision digest, review heads,
and target pointers under the repository mutation lock. Setup apply follows the same pattern.
Feedback regeneration returns the new revision and `review_resolution` ID in a typed result. Exact
Rust/JSON field names, nullability, enum spellings, limits, and error variants are frozen in the
implementation plan's first contract task and may not drift independently between Core, CLI,
fixtures, and Skill references.

### 13.3 Skill intents

The canonical Skill recognizes:

- setup/start/repair;
- summarize a selected Asset;
- explicitly register a selected Asset as Knowledge;
- summarize the Inbox;
- accept/reject the post-summary knowledge question;
- show status/queue/item;
- approve, request changes, or defer after an exact review display;
- add or show an explicit user judgment without LLM rewriting;
- inspect Git sync state and run only an explicitly approved bounded sync step;
- retry the Core-reported recoverable step.

The Skill stays concise. Detailed JSON schemas and recovery maps live in one-level references;
deterministic repeated orchestration belongs in Core commands or bundled scripts, not copied shell
logic.

## 14. Diagnostics and recovery UX

Every actionable failure returned to a person has three parts:

```text
Problem: what failed in user language
Impact: what was and was not changed
Next action: one concrete safe recovery step
```

Examples:

- offline Drive placeholder: open/download the file, then retry;
- stale review: display the current revision again;
- duplicate: show the existing record rather than fail generically;
- changed registered file: register as a new Asset or restore the original;
- lock contention: retry after the reported owner/deadline; do not clear automatically;
- partial Inbox batch: preserve successful items and report only failed/blocked items;
- invalid KB schema: create/select a v0.3 KB; never mutate the old one;
- Skill/CLI version mismatch: show both versions and the exact approved update action.

`mko doctor` human output includes failing component, sanitized path/record identity, error code,
whether retry is safe, and the exact next command or user action. JSON-v2 keeps structured details.

## 15. Safety and trust rules

- Source bytes, metadata, locators, extracted blocks, and semantic text are untrusted data;
- no document content may alter tools, permissions, approval, Git, setup, or review policy;
- only the Core writes canonical managed records;
- every durable semantic response is bound to the exact prepared bundle and Asset fingerprint;
- approval is bound to actual displayed bytes/revision, not a caller-supplied front-matter value;
- all scans are bounded by entries, bytes, depth, and elapsed deadline;
- file opens use no-follow/handle-based validation and revalidate identity after reads;
- publication uses managed locks and compare-at-commit validation;
- every cooperating v0.3 mutation uses the same repository mutation lock, preventing target
  pointer changes during multi-target review publication;
- secret material and machine paths remain outside Git;
- no automatic deletion, migration, approval, promotion, commit, or push;
- direct editing of managed records can invalidate approval and is reported rather than silently
  accepted;
- concise knowledge extraction respects copyright and does not reproduce documents in bulk.

Implementation follows TDD and updates Core, CLI, tests, Skill policy, forward scenarios, and docs
together.

### 16.1 Setup

- rerun idempotency;
- partial writer failure and honest rollback reporting;
- old v0.2 KB blocks before mutation;
- user-owned Obsidian files are not overwritten.
- unsupported/missing Obsidian receives the plain-Markdown fallback without a false readiness
  claim;
- second-device provider marker mismatch and logical-locator fingerprint reconciliation;
- dirty, stale, diverged, conflicted, and clean fast-forward Git sync states.

### 16.2 Asset and extraction

- outside-Inbox copy, inside-Inbox registration, duplicate reuse, and same-name/different-content;
- offline/recall placeholder classification without opening content;
- fingerprint changes before/during extraction;
- `prepared-content-v2` schema, bounds, locator validation, and bundle/Asset binding;
- canonical bundle digest, local-cache loss, deterministic re-extraction, and mismatch-as-new-basis;
- hostile embedded instructions remain data;
- generic extractor interface exercised with PDF and a deterministic fake non-PDF extractor.

### 16.3 Source and Knowledge

- summarize then decline/defer knowledge creation;
- summarize then accept knowledge creation;
- explicit knowledge intent skips only the question;
- Source facts have valid locators;
- LLM interpretation/hypothesis is separately labeled;
- counterarguments/uncertainty validation;
- `user_judgment` cannot be populated by a semantic response;
- high-risk domain response requires counterarguments and verification questions;
- exact user judgment creates a human annotation while semantic output cannot set it;
- identical writes are idempotent and concurrent writes report accurate outcomes.

### 16.4 Review and feedback

- unified queue includes pending Source and Knowledge and excludes approved records;
- full show/card includes synthesis, concept body, tags, locators, analysis, and uncertainty;
- approve all and selective approve;
- request changes persists exact feedback and target revision;
- defer is explicit and not inferred from unknown input;
- regeneration preserves the prior approved revision and returns to unreviewed;
- stale/raced/manual-modified snapshots cannot be approved;
- approval and review event publish together or neither does;
- one multi-target immutable approval event derives all-or-nothing Source/Knowledge approval;
- immutable revision bodies preserve exact diffs across restart and before Git publication;
- review sessions are expiring, single-use, non-replayable, owner-only, and host/TTY gated;
- search hides unreviewed Knowledge by default;
- no-follow, deadline, byte, and entry limits for list/search/queue.

### 16.5 Inbox, dashboard, and integration

- mixed batch with success, duplicate, blocked, offline, and invalid PDFs;
- retry resumes from Core state without redoing successful work;
- live Obsidian Bases display canonical states and links;
- dashboard repair affects only manifest-owned paths;
- end-to-end Skill integration for setup, summary, knowledge question, feedback, diff, and approval;
- manual Google Drive Stream smoke recorded as pending/pass/fail without fabricated evidence.

### 16.6 Skill forward testing

Use fresh-context subagents with raw Skill artifacts and realistic user prompts, including:

- "My Knowledge OS 시작해줘";

## 17. Acceptance criteria

v0.3 is complete when:

- a new user with the Skill installed can say "My Knowledge OS 시작해줘" and reach a healthy
  Personal KB without manually editing configuration files;
- setup can connect the same private KB on macOS and Windows using machine-local provider paths;
- setup verifies the same provider marker and a clean/non-diverged Git state before second-device
  writes;
- selecting a readable PDF and saying "이 PDF 요약해줘" produces a checked Source summary and
  asks once whether to create Knowledge;
- saying "이 PDF 지식으로 등록해줘" produces checked Source and Knowledge drafts without asking
  that question;
- the user can inspect a complete review card, submit natural-language feedback, see a new revision
  diff, and explicitly approve the exact displayed revision;
- exact previous and current revision bodies remain available independent of whether the user has
  committed to Git;
- an old or changed displayed revision cannot be approved;
- neither prompt text nor the Skill alone can authorize approval: a trusted host approval surface
  or real TTY confirmation is required;
- approved Knowledge is searchable and visible in the Obsidian Knowledge Library while unreviewed
  Knowledge stays out of default search;
- Inbox batch processing preserves partial successes and provides one safe next action per failure;
- the v0.3 KB contract is media/provider extensible even though only Google Drive filesystem PDFs
  are implemented;
- automated format, clippy, unit, integration, golden, concurrency, Skill-policy, and forward tests
  pass;
- the user-assisted live Google Drive smoke record is honest and complete before release.
