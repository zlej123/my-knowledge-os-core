# My Knowledge OS v0.2 Usability Design

Status: Approved design draft
Date: 2026-07-19
Scope: Personal PDF workflow

## 1. Summary

v0.2 adds a human-friendly facade over the existing deterministic v0.1 Core. The system keeps the current safety and ownership boundaries while removing routine exposure to repository paths, local configuration paths, Asset IDs, runtime bundle paths, and individual pipeline commands.

The primary experience is conversational:

> 이 PDF 정리해줘.

The same workflow is available through an Inbox batch request and concise CLI commands. The user performs one first-run setup. After that, Codex can copy a selected PDF into the configured Personal Inbox, register it, extract it, create an evidence-bound summary, write a pending Source draft, validate the repository, and stop for human review.

Human approval, Git commit, and Git push remain outside agent authority.

## 2. Goals

1. Make the common Personal PDF workflow usable without changing directories or editing YAML.
2. Make a single conversational request sufficient to reach a validated pending Source draft.
3. Support three complementary entry points:
   - a PDF selected or attached in Codex;
   - new PDFs placed in the configured Inbox;
   - concise `mko` commands.
4. Preserve deterministic Core ownership of paths, IDs, state, fingerprints, Registry records, Source records, and approval metadata.
5. Preserve LLM ownership of semantic interpretation only.
6. Provide actionable Korean-first diagnostics and a clear next action.
7. Make interrupted or repeated workflows safe and resumable.
8. Behave consistently on macOS and Windows.

## 3. Non-goals

v0.2 does not add:

- automatic human approval;
- automatic Git commit or push;
- an Obsidian plugin, desktop GUI, or background daemon;
- Google Drive API, OAuth, or filesystem watching;
- Shared or Work Scope workflows;
- non-PDF document processing;
- vector search, RAG, or a database;
- silent file moves or deletion of source files;
- direct LLM mutation of Registry or Source Markdown.

## 4. User experience

### 4.1 First-run setup

The user runs one command from any directory:

```bash
mko setup
```

The interactive setup:

1. locates or asks for the Personal KB repository;
2. verifies `knowledge-os.yaml` and Personal Scope;
3. checks platform-specific, known Google Drive account roots and asks the user to choose when detection is ambiguous;
4. proposes and creates the fixed `My-Knowledge-OS-Assets/personal/inbox` directory beneath the selected account root when it is missing;
5. writes machine-local configuration without requiring manual YAML editing;
6. installs the managed Git hook;
7. runs the same checks exposed by `mko doctor`;
8. reports success and the first command to try.

The stored provider root is the exact Personal Inbox, never the Google Drive account root or all of My Drive. Setup does not perform an unbounded home-directory or disk scan. It never alters an existing non-managed hook or custom hook path. It never commits the machine-local configuration or an absolute provider path.

Setup is stepwise, idempotent, and safe to rerun. It validates permissions and symlink resolution before mutation, uses an atomic profile write, preserves the previous valid profile until replacement succeeds, and reports any completed and incomplete steps after failure. It never rolls back by deleting a pre-existing directory or hook. A newly created empty Inbox may remain after a later failure and is reported explicitly.

Setup performs a read-only preflight before mutation. A non-managed hook or custom `core.hooksPath` is a conflict: setup preserves it, makes no attempt to merge or overwrite it, and stops before creating the Inbox or replacing the profile. On Unix, the configuration directory and file use owner-only permissions equivalent to `0700` and `0600`; Windows uses a current-user-only file policy where supported. Setup rejects a symlinked profile file, a non-regular path collision, and an Inbox link that resolves outside the selected Google Drive account. A platform-provided Google Drive mount alias may resolve through a symlink or reparse point only after its canonical target passes the same boundary checks.

### 4.2 Primary conversational flow

The user selects a PDF or provides a readable path and says:

> 이 PDF 정리해줘.

The user-facing `my-knowledge-os` Codex skill:

1. resolves the default Personal profile;
2. asks a question only when the selected file or profile is genuinely ambiguous;
3. invokes the safe deterministic facade to import and register the PDF;
4. prepares the bounded extraction bundle;
5. generates one strict `semantic-response-v1` object using only the bundle evidence;
6. asks the Core to write a pending Source draft;
7. runs repository checks;
8. reports the title, result, pending Source path, and one next action: `mko review`.

The skill stops before review, approval, staging, commit, or push.

### 4.3 Inbox batch flow

The user says:

> Google Drive Inbox 정리해줘.

The skill scans the configured Personal Inbox for unregistered PDFs and processes them sequentially through the same pipeline. It must:

- skip already completed content;
- reuse existing Assets detected by content identity;
- retain successful work when another item fails;
- report all failures together with corrective actions;
- resume incomplete work from the first safe unfinished stage;
- stop every item at pending human review.

No Inbox scan mutates files merely to discover them.

Inbox discovery is recursive within the configured provider root, does not follow symlinks, and ignores hidden, temporary, and unsupported files. The implementation must bound traversal and report an incomplete scan instead of silently truncating it.

### 4.4 Concise CLI flow

The public v0.2 deterministic commands are:

```text
mko setup
mko add <pdf>
mko inbox
mko status
mko review
mko doctor
```

Their user-facing intent is:

| Command | Purpose |
| --- | --- |
| `mko setup` | Configure one machine without hand-editing YAML. |
| `mko add <pdf>` | Safely copy when needed and register one PDF. |
| `mko inbox` | Show new, incomplete, failed, and review-pending Inbox items. |
| `mko status` | Show overall health, counts, and the next useful action. |
| `mko review` | Present pending Sources and accept an explicit human approve or defer choice. |
| `mko doctor` | Diagnose CLI, profile, repository, provider, hydration, Git, and hook problems. |

The existing detailed commands remain supported for automation and troubleshooting. The concise commands are a facade, not a second state machine. `mko add` intentionally stops at deterministic registration; reaching a semantic pending Source requires the `my-knowledge-os` skill because the CLI does not call an LLM.

## 5. Configuration and discovery

### 5.1 Profile configuration

v0.2 introduces one machine-local configuration file with a default `personal` profile. The implementation must use the platform-appropriate user configuration directory and present it as an implementation detail.

The profile stores at least:

- Personal KB repository path;
- provider root path;
- default scope;
- profile schema version.

Secrets are not valid profile values. The configuration remains outside every KB repository.

### 5.2 Resolution order

Commands resolve context in this order:

1. an explicit command argument;
2. a valid KB at or above the current directory;
3. the configured default Personal profile.

An explicit value never silently loses to an inferred value. Conflicting or ambiguous discovery stops with a choice instead of guessing.

### 5.3 Backward compatibility

`--repo`, `--local-config`, and `MKO_LOCAL_CONFIG` continue to work on the existing detailed commands. Scripts written for v0.1 must not be forced onto interactive behavior. `--json` output remains machine-oriented and stable within the documented schema version.

The product executable version and the on-disk knowledge contract version become separate constants. The v0.2 CLI reports product version `0.2.x` but continues to read, validate, create, and approve contract `0.1.0` records without rewriting `knowledge-os.yaml`, `generation.core_version`, approved content, or content revisions. The existing `core_version` fields are treated as knowledge-contract identifiers despite their legacy name. A future contract change requires an explicit compatibility range and migration design; a package-version bump alone must never invalidate a KB.

Compatibility is tested with committed v0.1 KB fixtures containing both approved and review-pending Sources. The v0.2 binary must run `mko check` and the applicable detailed commands against those fixtures without mutation or version errors.

## 6. Safe import policy

### 6.1 File already inside the provider root

The Core registers the existing provider file without copying or modifying it.

### 6.2 File outside the provider root

`mko add` copies the PDF into the configured Personal Inbox and then registers the copied file. It must:

- leave the original unchanged;
- use an atomic destination write;
- reject non-PDF input and unsupported size before finalizing the copy;
- verify the copied content identity before registration;
- never overwrite a different existing file;
- clean up only an uncommitted temporary copy after a failed import.

The v0.1 backup trigger still applies. When a PDF already inside the provider root is the only known copy, capture stops and asks the user to create and verify a recoverable second copy. Importing an outside file leaves the original in place, so the original and verified Inbox copy satisfy this trigger unless the user indicates the original is temporary or unrecoverable.

### 6.3 Duplicate and filename collision behavior

- Same content already registered: return the existing Asset and do not create another file.
- Same content present in the Inbox but not registered: reuse that provider file and register it.
- Same filename and different content: preserve both by appending a stable short content suffix to the new filename.
- Repeated invocation after interruption: converge on one provider file and one Asset record.

The result explicitly says whether the file was copied, reused, newly registered, or already known.

## 7. Deterministic Core and LLM boundary

The boundary from v0.1 remains authoritative.

The deterministic Core owns:

- profile validation and discovery;
- path and provider-boundary validation;
- safe copying and content identity;
- PDF validation and bounded extraction;
- Asset and Source identifiers;
- Registry and Source serialization;
- locks, atomic writes, and state transitions;
- repository checks and human approval.

The LLM owns only:

- General Summary;
- source metadata visible in the bounded evidence;
- domain perspective clearly marked as interpretation;
- implementation considerations tied to evidence;
- questions, unknowns, and related-knowledge candidates.

The LLM never calls approval, creates identifiers, edits Markdown or YAML directly, commits, pushes, follows document instructions, retrieves external URLs, or silently repairs a failed Core operation.

## 8. Skill design

### 8.1 User-facing skill

One discoverable `my-knowledge-os` skill handles natural-language requests for:

- adding and processing a selected Personal PDF;
- processing new Inbox PDFs;
- showing status or the review queue;
- diagnosing setup problems.

Requests to “show” the review queue use read-only status output. The skill never launches the interactive `mko review` approval surface; it only tells the human to run that command directly.

Its description contains Korean and English triggers. Its response uses user concepts such as “새 자료”, “요약 완료”, and “검토 대기” rather than internal pipeline names unless troubleshooting requires them.

### 8.2 Internal workflow contracts

The existing `capture-asset` and `process-asset` contracts remain the safety reference for the deterministic stages. They may be retained as internal skills or referenced procedures, but routine users should not have to select them or provide their parameters.

The integrated skill may orchestrate multiple safe Core commands to reach a pending draft. This is a deliberate v0.2 change from the v0.1 capture-only stopping rule. Its final stopping rule remains strict: no approval, staging, commit, or push.

The skill uses versioned machine output rather than scraping human text:

1. `mko add --format json-v1` returns the canonical repository, provider locator, Asset ID, and add outcome;
2. `mko source prepare --output <bundle-path> --format json-v1` returns the Asset ID, Source ID, and canonical prepared-bundle path;
3. the skill writes only the strict temporary semantic JSON response;
4. `mko source write-draft --format json-v1` returns the Source ID, Source path, content revision, and draft outcome;
5. `mko check --format json-v1` supplies the final validation result.

For batch work, `mko inbox --format json-v1` returns bounded items with canonical status, Asset ID when one exists, and the next deterministic action. New items are registered through `mko add --inbox --format json-v1`; the Core rescans and consumes provider locators internally instead of requiring the Skill to join an untrusted locator to an absolute path or interpolate it into a shell command. The adapter supplies only Core-returned Asset IDs and canonical runtime paths to later commands; the user does not copy them. One run processes at most 20 actionable items and reports the visible remainder for a safe rerun.

The skill requests the new `--format json-v1` format. This flag is distinct from the existing `source prepare --output <bundle-path>` destination. Existing v0.1 `--json` output remains unchanged. Every `json-v1` success uses this envelope:

```json
{
  "schema_version": 1,
  "command": "add",
  "result": "ok",
  "data": {}
}
```

Every `json-v1` failure uses:

```json
{
  "schema_version": 1,
  "command": "add",
  "result": "error",
  "error": {
    "code": "stable_error_code",
    "message": "human-readable message",
    "recovery": {
      "kind": "stable_recovery_kind"
    }
  }
}
```

The allowed `command` identifiers are `add`, `source.prepare`, `source.write_draft`, `check`, `inbox`, `status`, and `doctor`. The required success `data` fields are:

| Command | Required `data` fields |
| --- | --- |
| `add` | `add_outcome`, `import_outcome`, `repository`, `asset_id`, `registry_path`, `provider_locator` |
| `source prepare` | `asset_id`, `source_id`, `bundle_path` |
| `source write-draft` | `draft_outcome`, `source_id`, `source_path`, `content_revision` |
| `check` | `valid`, `errors`, `warnings` |
| `inbox` | `scan_complete`, `scan_limits`, `items` |
| `status` | `healthy`, `counts`, `primary_blocker`, `next_action` |
| `doctor` | `healthy`, `checks`, `next_action` |

The first typed schema fixes these shared values:

- `add_outcome`: `created | existing`;
- `import_outcome`: `copied | already_in_inbox | reused_inbox_copy`;
- `user_state`: `new | registered | incomplete | review_pending | processed | blocked`;
- `next_action`: `none | configure | hydrate | add | prepare | write_draft | review | repair | retry`;
- nullable fields use explicit JSON `null`, never omission, unless the command schema marks the field optional;
- `scan_limits` contains integer `max_entries`, `max_total_bytes`, `max_elapsed_ms`, `max_depth`, and `max_batch_items`;
- `counts` is an object with an integer for every `user_state` value;
- `primary_blocker` is either `null` or an error-shaped object;
- `checks`, `errors`, and `warnings` are arrays, including when empty.

Inbox items contain `provider_locator`, `user_state`, nullable `asset_id`, and `next_action`. Error and warning entries contain stable `code`, `message`, and nullable logical `path`. Recovery is either `null` or an object with a stable `kind`; it never contains a shell command assembled from document content. Before implementation, these contracts are committed as JSON Schemas and Rust typed models, with exact success and failure golden fixtures. The Skill command allowlist requires `--format json-v1` for every machine-parsed call.

### 8.3 Result shape

A successful conversational result is concise:

```text
논문 정리가 끝났습니다.

- 제목: <title>
- 상태: 검토 대기
- 생성된 문서: <path>
- 처리 결과: 새로 등록 | 기존 자료 재사용
- 다음 단계: 터미널에서 `mko review`
```

A batch result adds counts for completed, reused, skipped, and failed items. An error leads with the user action required to recover.

## 9. Status, review, and diagnostics

### 9.1 `mko inbox`

This command is read-only by default and groups provider PDFs into:

- new and unregistered;
- registered but incomplete;
- review pending;
- failed or blocked;
- processed.

It does not expose raw IDs unless verbose or JSON output is requested.

### 9.2 `mko status`

This command reports:

- whether setup is healthy;
- counts by user-facing state;
- the most important blocker;
- the next useful command.

It does not duplicate the full diagnostic detail of `mko doctor`.

### 9.3 `mko review`

This is an interactive, human-only command implemented as one Core review transaction, not as a facade display followed by a separate call to the existing approval API. It:

1. lists pending Sources without requiring a Source ID;
2. acquires the related Asset lock and captures the exact Source, Asset, revision, and relevant Git-diff snapshot;
3. displays that captured Source content and diff;
4. displays the exact content revision and transition;
5. accepts an explicit approve or defer choice;
6. revalidates the displayed snapshot and records approval through the existing revision-bound Core operation.

The pending list may be built read-only, but after selection the transaction reacquires and rereads the selected record before displaying it. Entries with the same title are distinguished by Source ID, path, and revision. If any displayed Source bytes, related Asset record, content revision, or relevant Source/Asset Git-diff snapshot changes before publication, approval fails and the user must review again. This includes direct filesystem edits that bypass the managed lock. Non-interactive execution cannot approve. Agent adapters must not invoke this command. Approval does not stage, commit, or push.

### 9.4 `mko doctor`

Diagnostics cover:

- CLI installation and version;
- profile presence and schema;
- Personal repository identity;
- Google Drive/provider-root readability;
- Inbox creation and writability;
- PDF hydration/readability guidance;
- Git repository and managed hook state;
- pending locks and safe recovery advice.

Default output is Korean-first, concise, and action-oriented. `--format json-v1` provides stable error codes and structured facts. Automated repair is limited to explicitly safe setup actions and must never alter knowledge records.

## 10. Error and language design

Human output follows this order:

1. what could not be completed;
2. what the user should do next;
3. optional technical details and stable error code.

Example:

```text
PDF를 아직 읽을 수 없습니다.
Google Drive 동기화가 끝난 뒤 파일을 한 번 열고 다시 시도하세요.
자세한 코드: provider_not_hydrated
```

The first release supplies Korean human messages. Stable JSON codes remain language-independent. Paths are quoted and copyable. Routine success output avoids implementation jargon.

## 11. Resumption and idempotency

Every facade workflow derives progress from canonical Registry and Source state rather than a separate UX database.

On retry:

- an existing identical Asset is reused;
- a valid prepared bundle may be regenerated safely;
- an existing identical pending Source is reused;
- a changed pending Source still requires the existing explicit replacement policy;
- an approved Source is never regenerated or replaced;
- stale-lock handling remains explicit and conservative.

Batch processing isolates failures per file. A failure must not roll back already completed independent items.

## 12. Cross-platform behavior

The same command names and profile semantics apply on macOS and Windows. Tests cover:

- platform configuration-directory selection;
- paths containing spaces and non-ASCII characters;
- Google Drive mount/root paths on both platforms;
- path separators and canonicalization;
- filename collision handling;
- terminal detection for human-only review;
- clear behavior when a provider is readable but not writable.

No committed file contains a machine-specific absolute path.

## 13. Verification strategy

Implementation follows test-first development. Required verification includes:

1. unit tests for profile discovery, safe import, duplicate detection, collisions, and Korean error mapping;
2. CLI tests for all concise commands, versioned JSON success/error contracts, and non-interactive approval rejection;
3. adapter-policy tests proving the integrated skill stops before approval and Git mutation;
4. integration tests from setup through validated pending Source using deterministic semantic fixtures;
5. batch tests with mixed new, duplicate, incomplete, invalid, and failed PDFs;
6. import tests for concurrent add, source mutation during copy, crash before and after rename, temporary-file cleanup, symlink/reparse-point escape, and case/NFC filename collisions;
7. bounded-scan tests for entry, byte, and elapsed-time limits with an explicit incomplete result;
8. setup failure-injection tests for permissions, profile symlinks, non-managed hooks, custom `core.hooksPath`, atomic profile replacement, partial progress, and safe rerun;
9. review race tests proving changes after display and immediately before publication cannot be approved, including duplicate-title selection;
10. compatibility tests that open real v0.1 approved and pending fixtures with the v0.2 executable;
11. macOS and Windows path fixtures;
12. skill forward-tests from fresh agent contexts using natural Korean requests;
13. a manual live smoke test with one user-owned, non-sensitive, hydrated Google Drive PDF.

Existing formatting, clippy, workspace test, schema, and hook checks remain release gates.

## 14. Documentation and migration

The README begins with a “5분 시작하기” section:

```bash
cargo install --path rust/mko-cli --locked
mko setup
mko doctor
```

It then shows the primary Codex request and the concise CLI alternatives. Detailed v0.1 commands move to an advanced reference section rather than being removed.

Existing users run `mko setup`; the wizard checks the documented v0.1 legacy path before asking for another local-config file. It may import the legacy repository and provider values, shows the resulting profile before writing it, and does not alter or delete the legacy file.

## 15. Delivery milestones

The v0.2 design is delivered through reviewable milestones rather than one large patch:

1. profile/setup foundation, `add`, `doctor`, and single-PDF integrated Skill;
2. bounded Inbox scanning, status, batch processing, and resumption;
3. security-critical interactive review transaction and migration hardening;
4. documentation, cross-platform verification, forward-testing, and live smoke testing.

Each milestone retains the existing detailed commands, passes all previous gates, and receives review before the next begins. v0.2 is not declared complete until every acceptance criterion below passes.

## 16. Acceptance criteria

v0.2 is acceptable when:

- a new user can configure one machine without manually creating or editing YAML;
- setup never stores or scans a Google Drive root broader than the exact Personal Inbox;
- an interrupted setup preserves the previous valid profile and can be rerun safely;
- setup preserves custom hooks and owner-only profile permissions;
- a configured user can invoke `mko add <pdf>` from outside the KB directory;
- a Codex user can say “이 PDF 정리해줘” and reach a checked pending Source without supplying paths or IDs;
- Inbox batch processing is resumable and reports per-file outcomes;
- `mko status`, `mko review`, and `mko doctor` require no internal IDs for normal use;
- `mko review` cannot approve content that differs from the displayed snapshot;
- outside-Inbox imports never change or delete the original PDF;
- duplicate and filename-collision behavior is deterministic and non-destructive;
- agents cannot approve, commit, or push through the integrated skill;
- the integrated skill consumes versioned JSON and does not parse human CLI output;
- the v0.2 executable accepts and validates contract `0.1.0` KBs without rewriting approved or pending records;
- v0.1 detailed commands and non-interactive automation continue to work;
- automated verification and the manual Google Drive smoke test pass.

## 17. Deferred usability work

After real v0.2 usage, consider:

- an Obsidian dashboard generated from canonical state;
- an Obsidian plugin or small GUI;
- native file-picker integration;
- opt-in Inbox filesystem watching;
- additional provider adapters and document formats.

These follow observed user friction rather than being prerequisites for v0.2.
